# create-mercury 0.5.0

This pre-1.0 release changes infrastructure, environment configuration, and todo ownership. The published 0.4.1 starter used Docker Postgres, a Node API, and Caddy. Version 0.5.0 runs React Static Assets and Hono in one Cloudflare Worker with a same-origin API.

## What changes

Neon Postgres connects through Hyperdrive and `pg`. Drizzle remains the ORM, with committed migrations and stable packages. Docker configuration is removed.

The starter gains managed Neon Auth with signup, signin, email verification and resend, password reset, and cookie sessions. The API derives each todo's text `ownerId` from the verified session and filters reads by that owner. Anonymous todo requests return HTTP 401.

Runtime database credentials have restricted grants. Migrations use a separate database-owner credential. Development and staging use separate Neon branches, and production uses a separate project. Staging and production have explicit migration and deployment commands, separate Workers, Hyperdrive configurations, Auth URLs, and cookie secrets. Generic branch previews are disabled.

The template includes updated official Cloudflare and Neon skills and licensed Postgres guidance. Release publishing now requires live Neon Auth and database integration before the packed CLI smoke test.

## Start a new project

Create a project with `pnpm create mercury@0.5.0 my-app`. Scaffolding and dependency installation need no cloud credentials. Running the app requires Neon setup.

Follow [Connect development services](https://github.com/arvemy/mercury/blob/v0.5.0/cli/project-readme.md#connect-development-services). Run `neon init --services postgres,auth` and `neon deploy`, configure branch Auth settings, and fill the local environment files. Apply migrations, create the restricted runtime role, and set the local Hyperdrive connection and cookie secret before `pnpm dev`.

For deployment, follow [Configure staging and production](https://github.com/arvemy/mercury/blob/v0.5.0/cli/project-readme.md#configure-staging-and-production). Configure Cloudflare access, Hyperdrive, the exact app origin, and environment secrets before using `pnpm deploy:staging` or `pnpm deploy:production`.

## Upgrade an existing project

Existing generated projects do not update when you install a newer CLI. Compare your project with a fresh 0.5.0 scaffold and port your changes after reviewing the new infrastructure and configuration.

A populated 0.4.1 database needs a reviewed migration plan and recovery point. The required text `ownerId` column has no default, so the migration refuses existing ownerless rows. No automatic data or identity migration is included. If you used an intermediate Clerk branch, review an explicit Clerk-ID-to-Neon-ID mapping before changing ownership. See [Keep existing identity ownership](https://github.com/arvemy/mercury/blob/v0.5.0/cli/project-readme.md#keep-existing-identity-ownership).

Keep the pinned Miniflare transport patch. It mitigates local preview connection failures while the upstream issue remains unresolved. Before production, [validate your deployment](https://github.com/arvemy/mercury/blob/v0.5.0/cli/project-readme.md#validate-a-deployment-and-recover), including production SMTP, verification and reset emails, and custom-domain DNS and TLS. Passing `workers.dev` checks does not prove your custom domain works.
